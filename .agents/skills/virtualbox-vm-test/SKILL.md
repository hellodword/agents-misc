# VirtualBox VM Tests

1. Identify the prepared executor, required Windows/Linux templates, topology and evidence. Read [execution](references/execution.md) and apply the [VM test conventions](../../rules/vm-tests.md). Missing host, image or baseline prerequisites belong to the [VM Test MCP administrator guide](https://github.com/hellodword/agents-misc/blob/master/tools/vm-test-mcp/preparation.md).
2. Prepare the batch's scripts, dependencies and assertions locally. Call `service_get` and the compact active `task_list`, select each node's startup mode using the VM test conventions, then call `lab_create` with the complete node list and a batch deadline. Repeated templates create independent linked clones. Media requests must fit the advertised policy and default off. Poll the operation and task before using node IDs.
3. Upload project inputs, then use `command_start` with guest argv. Probe Python/Docker/Compose through PATH and actual version/import commands; install missing task dependencies inside the clone, using offline uploads when useful. Linux nodes can run Docker/Compose. Use LAN names for guest-to-guest traffic and `endpoint_open` for allowed development-container TCP/UDP access. Public IPv4 egress can be toggled; a degraded router requires explicit `network_recover` after inspecting its task events.
4. Keep test code, assertions and dependencies in the tested project. For Windows control/image automation, read [standalone automation](references/automation.md) and select the product or executor-maintenance scope. Automatic login is optional: use screenshots and native input to inspect/login/unlock when needed. Use `node_display` and `lab_gui_set` for the exposed display policies, and capture evidence as needed. Inspect uncertain input receipts before sending another action; application success requires its own assertion.
5. Use `node_get` and `task_diagnose` for preparation or runtime faults; `node_exec` provides short Guest Control commands independently of the supervisor. Preserve a running fault for bounded diagnosis; do not automatically restart or recreate nodes. Retain evidence before release and follow the shared batch lifecycle. Retry ended-task VirtualBox cleanup through `task_cleanup` after inspecting resource errors.
6. Collect reports and capture artifacts, then submit the caller's conclusion and explanation through `task_finish`. Use `task_cancel` to abandon a queued or preparing task. Wait for complete cleanup before local rework, and use a new task for the next batch. Report task/node IDs, assertions, command exits, evidence and cleanup; retain unresolved evidence for diagnosis.
