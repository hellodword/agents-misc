# VM Test Execution

- Select a prepared, authorized executor and registered template. Reuse an established project-local flow when it meets the task. When a session provides neither `vm_test` MCP tools nor an explicitly authorized `--config /abs/client.yaml` path, run local container validation gates when they cover the task, or report the missing host client prerequisite directly without probing private host directories. Environment preparation belongs to a separately authorized setup task and its manual guide.
- Default to headless VM execution. Select a host-visible GUI when explicitly required by the user or scoped project requirements, or when verified evidence shows that the test depends on that frontend. State the supporting requirement or evidence and apply GUI only to the nodes that need it.
- Use the service's `execution_id`, resource IDs, scoped transfer URLs and artifact records. Retry identical mutations with the same `(tool, request_id)` pair; give new executions or changed parameters a fresh `request_id`. Prefer evaluation-time deterministic synthetic credentials in remotely submitted VM tests so store derivations stay reproducible across client and executor stores.
- Keep execution bounded by task deadlines. HTTP connection state is separate from task state; reconnect to inspect the original task before submitting another execution.
- Prepare inputs locally, then acquire the shared executor for a continuous test batch. After tests and bounded diagnosis, finish or cancel the task and confirm runtime resource release before the next executor batch. If release requires administrator intervention, preserve the task identity, ownership observations and concrete cause, report the blocker, and continue independent local edits, analysis or reporting. Evidence collection and transfer have their own completion state; pending evidence does not establish VM occupancy. A later batch rejoins the queue with a new execution identity. Continued occupancy needs concrete work, a reason and a deadline; record extension reasons through the service. No running commands or a disconnected client alone proves that a service fixture is idle.
- Interpret process exits, test assertions, resource release, evidence collection and handoff as separate observations. Declare expected command exits when a test accepts codes beyond zero; use driver receipts for NixOS assertions and the caller’s explicit conclusion for a VirtualBox lab. Recover the original execution after resolving its recorded resource or evidence cause.
- Treat native input delivery and application success as separate observations. Inspect an unconfirmed delivery before sending another action. Keep capture identities and evidence errors alongside the task's cleanup result.
- Let active tasks finish before switching virtualization backends. Unrelated administrator VMs are not task-owned cleanup resources. Confirm actual cleanup before releasing resources; preserve evidence when cleanup is unresolved.
- Use existing task authorization and the target's configured capabilities for VM settings, power and device operations. Read effective capabilities before use and treat policy rejection as an execution boundary.
- Retain useful failure logs, screenshots and reports before destroying disposable clones. Report task identity, assertions, exit status, evidence locations and cleanup state. Describe graphics and media capabilities from the actual operation measured.

- Optional guest tools belong to the test workflow: probe PATH and execution, then install missing task dependencies inside disposable nodes. Source-baseline changes remain administrator preparation. Desktop tests may log in/unlock through native input; automatic login is a convenience, not an executor prerequisite.
